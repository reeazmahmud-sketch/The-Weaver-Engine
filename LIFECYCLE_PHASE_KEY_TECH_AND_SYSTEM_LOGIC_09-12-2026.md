**Team:** 1 — Architects · **Phase name (lifecycle):** Discovery

### 2.1 Key tech / system logic

| Rule | Detail |
|------|--------|
| Search-driven | Web-scraped / domain evidence + standard frameworks (MCP, hooks, skills, enterprise agent patterns) ground blueprints |
| Component map first | Goal, modules list, MCP/hook/extension/skill specs, I/O contracts, risks, human gates, acceptance criteria |
| Modular by default | Independent interoperable units — **not** monolith agents |
| Replaceability | Each mapped unit must be hotfixable (Team 3) and auditable (Team 4) |
| Portability | Relative / env-based paths; no machine-local hardcodes in product contracts |
| Human gates | Ethics / irreversible / strategy pivots stay with CEO/Admin |

**Documentation & Component Map** — the Team 1 modular blueprint packet consumed by Team 2.

### 2.3 Handoff

Team 1 → Team 2 when blueprint packet + filled acceptance checklist are ready. Incomplete → **hold Discovery**; do **not** fake Execution.

## 6. Overarching orchestration & feedback logic

Master Orchestrator **1.0.0-APPROVED-DOCS-ONLY** already encodes the handoff packets for human session operators — **cite only; do not re-draft**.

### 6.1 Supervisor Agent coordination

The central **Supervisor Agent (Orchestrator)** manages data flow and handoffs across the four lifecycle phases (T1→T2→T3→T4). On the ship path, that facet is the **Deployment Orchestrator**. It enforces the **Self-Critique** gate before dual audit and Go/No-Go synthesis. It does **not** override Security Sentinel or Compliance Officer vetoes. Distinct from Master Orchestrator (**1.0.0-APPROVED-DOCS-ONLY** five-team handoff prompt).

### 6.2 Fail-safe entry gating (Self-Critique mandatory)

**Hard rule:** Team 4 must never evaluate a module for deployment until Team 3 completes a **Self-Critique** on it (Builder ships use the equivalent pre-audit packet).

**Producer:** Team 3 (hotfix) or Team 2 (Builder ship equivalent).  
**Enforcer:** Supervisor Agent.

| Rule | Behavior |
|------|----------|
| Incomplete Self-Critique | Return to submitter — **do not** open formal dual audit; **do not** synthesize Go/No-Go |
| Not a substitute | Self-Critique ≠ Security Sentinel / Compliance Officer audit |
| Fresh on re-entry | After any Vulnerability Report, prior Self-Critique must be redone |

**Minimum fields:** `module_id` / `module_type` · `what_changed` · `known_risks` · `blast_radius` · `rollback_plan` · `evidence_attached` · `human_gate_needed` · `self_critique_complete`

### 6.3 Closed-loop remediation (Vulnerability Report)

When Team 4 identifies a risk during auditing, the Deployment Orchestrator **blocks the CI/CD gate** and transmits a **Vulnerability Report** back to Team 3, re-engaging Team 3's **Chain-of-Thought Diagnostics** before re-audit.

**Canonical diagram — cite, do not restate:** [`AUTONOMOUS_AGENTIC_LIFECYCLE_FIVE_TEAM_FRAMEWORK_09-12-2026.md`](AUTONOMOUS_AGENTIC_LIFECYCLE_FIVE_TEAM_FRAMEWORK_09-12-2026.md) **§1.4.2** (Pre-Audit Self-Critique → dual-lens audit → Deployment Orchestrator risk-signal synthesis → Go/No-Go → Secure Production Deployment / Vulnerability Report → Team 3 CoT Diagnostics).

| Requirement | Detail |
|-------------|--------|
| One blocking Fail from either lens | ⇒ **No-Go** |
| Ship pause | Blocking report ⇒ no CI/CD Deploy for that unit / correlation id |
